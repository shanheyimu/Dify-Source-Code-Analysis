Dify 产品演进与技术对比

01Dify 是什么

🎯 产品定位

Dify 是一款开源的 LLM 应用开发平台，提供从 工作流编排、聊天机器人、RAG 知识库 到 Agent 智能体 的全链路能力。面向企业用户，强调开箱即用、可视化、低代码协作。

Workflow 工作流→ Chatbot 对话→ Agent 智能体→ Knowledge 知识库→ Plugin 插件生态

02版本演进时间线

从 2025 年 2 月首版至今，Dify 以平均 1.5 个月一次的节奏快速迭代，持续补齐生产级能力。

奠定 Dify 生态基础，实现工具/模型即插即用，Workflow 可通过 Agent 节点编排复杂智能体。

  • Plugin System — 引入 .difypkg 插件格式，支持工具、模型扩展
  • Plugin-based Tool & Model — 工具与模型全面解耦，统一插件化管理
  • Agent Node — Workflow 新增 Agent 节点，插件可定义 Agent 策略
  • Extension Plugin — 托管自定义服务，处理 Webhook 等外部事件
  • Dify Marketplace — 官方插件市场上线，支持发布/共享/下载

层职责说明说明

💬 换个视角：从用户使用流程理解七层

上面的表格是"职责"视角；实际使用时，用户是自顶向下一层层进入的：

① 交互层 — 用户面对的就是这一层：打开网页、点按钮、发消息，所有操作从这里进入
▼
② 应用层 — 在这里选择具体的 AI 应用：Chat 聊天、Workflow 工作流、Agent 智能体…
▼
③ 编排层 — 选中某个应用后进入编排（以 Workflow 为例）：它是整个流程的大脑，安排"先干什么、后干什么"、节点之间怎么串联
▼
④ AI 能力层 — 给大脑附加能力：接入 RAG 知识检索、加长短期记忆、挂外部工具
▼
⑤ 模型接入层 — 大脑要工作还需要"会思考"：切换不同大模型厂家（GPT / Claude / 本地模型），这一层屏蔽差异，随时可换
▼
⑥ 基础设施层 — 以上功能要跑起来离不开底座：数据存储、缓存加速、异步任务队列
▼
⑦ 对外服务层 — 最后是对外接口：与外部大模型、第三方系统、MCP 服务打交道

💡 逻辑七层是职责视角，源码六层是物理目录视角：逻辑上的"AI 能力层"在源码里分散于 core/ 多个目录；"基础设施层"对应 extensions/ + tasks/。逻辑分层便于理解职责，源码分层便于定位代码，两者互补。

📁 各层明细（点击标签或 ←/→ 键切换）

① 启动层 — 开机流程

相当于后端的"开机流程"：先把数据库、缓存、异步任务等零件装好，系统才能对外服务。

  • 创建应用实例 — app.py 是进程入口
  • 初始化扩展 — 按顺序装配数据库、Redis、Celery、登录、邮件、存储等（app_factory.py）
  • 全局钩子 — 每个请求进来前的校验、离开时的日志
  • 部署配置 — 生产服务器（gunicorn）与 Celery worker 入口

📍 关键位置：api/app.py、api/app_factory.py、api/extensions/

② 接入层 — 前台总机

相当于"前台总机"：所有外部请求都打到这里，按类型转给不同处理窗口。

  • 管理台入口 — 画布编排、应用配置、监控（console/）
  • 公开应用入口 — 聊天、表单、文件上传（web/）
  • 第三方集成入口 — 给外部系统调用的密钥 API（service_api/）
  • MCP 协议入口 — 对接外部 MCP 客户端
  • 公共装饰器 — 登录校验、权限校验、参数解析等（wraps.py）

📍 关键位置：api/controllers/

③ 业务层 — 部门经理

相当于"部门经理"：接到请求后，判断该调哪些底层能力，编排它们协同完成一件事。

  • 应用调度 — 按应用类型分发到聊天 / 工作流 / Agent 等生成器
  • 工作流管理 — 工作流定义、运行、恢复
  • Agent 管理 — 智能体的配置与编排
  • 知识库管理 — 数据集、文档、知识处理
  • 对话与消息 — 会话、消息记录
  • 文件与配额 — 文件上传处理、配额计费

📍 关键位置：api/services/

④ 领域层 — 技术车间

相当于"技术车间"：Dify 最核心、最复杂的地方，各种引擎在这里实现。

  • 应用运行框架 — 每种应用（Chat / Agent / Workflow）都有自己的生成器 + 执行器
  • 工作流引擎 — 节点怎么注册、怎么按序执行
  • Agent 引擎 — FunctionCall / CoT 等推理策略
  • RAG 管道 — 文本分块、向量化、检索、重排序
  • 工具系统 — 内置 / 自定义 / MCP / 插件四类工具
  • 模型管理 — 统一调用不同大模型
  • 插件系统 — 插件安装与调度

📍 关键位置：api/core/

⑤ 数据层 — 档案室

相当于"档案室"：所有数据都存在这里，负责存哪里、怎么读、怎么升级表结构。

  • 业务表 — 应用、对话、消息、数据集、账号等
  • 工作流表 — 工作流定义、运行记录、节点执行记录
  • 数据访问层 — Repository 封装数据库操作
  • 数据库迁移 — Alembic 管理表结构升级

📍 关键位置：api/models/、api/repositories/、api/migrations/

⑥ 基础设施 — 后勤仓库

相当于"后勤仓库"：存放各种通用工具和后台任务，谁需要谁拿。

  • 通用工具 — 加密、登录鉴权、JWT、分页、邮件发送等
  • 集中配置 — 系统所有配置项统一管理
  • 领域事件 — 应用 / 消息 / 数据集等变化的通知
  • 异步任务 — Celery 定时与后台任务
  • 工厂方法 — 文件解析、变量构建等复用逻辑

📍 关键位置：api/libs/、api/configs/、api/tasks/

🧠 领域核心 core/ 内部划分

core/ 是后端最复杂的目录，按业务领域细分、各自独立演进：

  • core/app — 应用运行框架：generator（生成器）/ runner（执行器）/ queue_manager（Redis 队列），统一支撑聊天、Agent、工作流三类应用
  • core/workflow — 工作流引擎：node_factory（节点注册与解析）/ workflow_entry（入口）/ nodes/（20+ 节点实现）/ variable_pool（变量池）
  • core/agent — Agent 引擎：FunctionCall / CoT / Plugin 三种策略 runner
  • core/rag — RAG 管道：splitter（分块）/ embedding（向量化）/ retrieval（检索）/ rerank（重排序）
  • core/tools — 工具系统：内置 / 自定义 / MCP / 插件四类工具统一管理
  • core/model_manager — 模型管理：多供应商 LLM 统一接入与调用
  • core/plugin — 插件系统：插件安装、调度、与插件守护进程通信

⚙️ 工作流执行：双线程 + Redis 事件流

一次工作流运行由 两个线程 协作完成，通过 Redis Topic 解耦，前端以 SSE 实时接收事件：

HTTP 入口→ Service 限流/配额→ Celery 异步→ GraphEngine 执行节点→ Redis 事件流→ SSE 前端
  • Worker 线程 — 真正执行 GraphEngine：拓扑执行节点、变量池传递数据、产出引擎事件，事件先送入进程内内存队列
  • 主线程 — 从内存队列读取事件转成 SSE 事件，由 _publish_streaming_response 发布到 Redis Topic；前端再经 retrieve_events 从 Redis 读取渲染
  • 懒启动 — 首个 SSE 订阅者接入时才触发 Celery 任务
  • 暂停快照 — Human Input 节点暂停时序列化整个运行时状态，恢复时反序列化续跑
  • 中间件层 — 持久化 / 限流 / 暂停 / 观测以 Layer 形式横切执行

🛣️ 端到端示例：一次工作流运行（附触发文件路径）

从前端点击"运行"到 SSE 实时输出，完整链路共 8 站，每一站都标注了触发的真实文件与关键函数。

第 1 站

🎯 前端发起请求

用户在工作流画布点击"运行"，浏览器向管理台 API 发送 POST 请求。

  • 触发位置 — web/app/（前端画布组件）
  • 请求 — POST /console/api/apps/{app_id}/workflows/draft/run
  • 请求体 — {"inputs": {...}, "response_mode": "streaming"}
第 2 站

🚦 Controller 接收

DraftWorkflowRunApi.post() 经过 8 层装饰器鉴权后，解析参数并调用服务层。

  • 触发文件 — api/controllers/console/app/workflow.py（L1074 DraftWorkflowRunApi → L1093 post）
  • 装饰器链 — @setup_required / @login_required / @rbac_permission_required / @with_session / @get_app_model(mode=[WORKFLOW])
  • 动作 — DraftWorkflowRunPayload 解析 → AppGenerateService.generate(streaming=True)
第 3 站

🔒 Service 限流 + 配额

AppGenerateService 先做配额预留和应用级限流，再按 AppMode 分发到不同生成器。

  • 触发文件 — api/services/app_generate_service.py（generate L100 → _run_with_guardrails L128 → _dispatch_generate L160）
  • 配额 — QuotaService.reserve(QuotaType.WORKFLOW)，超限抛 InvokeRateLimitError
  • 限流 — RateLimit(app_id).enter()
  • 分发 — case AppMode.WORKFLOW（L293）
第 4 站

🧵 Celery 异步任务提交

Controller 返回 StreamingResponse 后并不会立即启动 Workflow， 而是在客户端成功建立 SSE 订阅后，通过 on_subscribe() 回调将任务提交给 Celery， 实现"先建立流，再开始执行"。

  • 触发文件 — api/services/app_generate_service.py L311-314（on_subscribe → workflow_based_app_execution_task.delay）
  • 执行任务 — api/tasks/app_generate/workflow_execute_task.py（workflow_based_app_execution_task → _AppRunner.run）
  • 运行环境 — Celery Worker 调用 _setup_flask_context(user) 重建 Flask 应用上下文，使异步任务能够正常访问 current_app、数据库会话等资源
第 5 站

🏭 WorkflowAppGenerator 构建

解析上传文件、构建应用配置实体，然后启动双线程模型（worker 执行 + 主线程读事件）。

  • 触发文件 — api/core/app/apps/workflow/app_generator.py（generate L150 → WorkflowAppGenerateEntity L214 → _generate L321）
  • 实体 — application_generate_entity（贯穿全程的核心对象）
  • 双线程 — worker 线程 _generate_worker L616 + 主线程 _handle_response L701
第 6 站

🔩 WorkflowAppRunner 组装引擎

构建变量池、执行图、命令通道，创建 WorkflowEntry 并挂载中间件层，最大的职责就是把 Workflow Engine 需要的所有运行环境准备好。

  • 触发文件 — api/core/app/apps/workflow/app_runner.py（run L73）
  • 变量池 — VariablePool + 系统变量 + 用户输入（L109-138）
  • 入口 — WorkflowEntry 创建（L170-184）
  • 中间件 — WorkflowPersistenceLayer / PauseStatePersistenceLayer（L186-202）
  • 执行 — workflow_entry.run()（L204）
第 7 站

⚙️ WorkflowEntry → GraphEngine 执行节点

图引擎按拓扑顺序执行节点，变量池传递数据，每个节点产出引擎事件。

  • 触发文件 — api/core/workflow/workflow_entry.py（run L250 → iter_dify_graph_engine_events）
  • 引擎 — GraphEngine.run() 拓扑执行节点
  • 事件 — 每个引擎事件交给 _handle_event 分发到进程内事件队列
第 8 站

📡 事件回流 → SSE 前端

引擎事件先经进程内队列从 worker 线程送到主线程，主线程转成 SSE 事件后由 Celery 任务发布到 Redis Topic，前端经 retrieve_events 读取后实时渲染。

  • 进程内分发 — _handle_event → queue_manager.publish → 进程内内存队列（worker 线程 → 主线程，不经过 Redis）
  • 发布到 Redis — Celery 任务 _publish_streaming_response（api/tasks/app_generate/workflow_execute_task.py L405-426）→ topic.publish（channel:{mode}:{workflow_run_id}）
  • 读取 — api/core/app/apps/message_based_app_generator.py（retrieve_events L316）从 Redis Topic 读取
  • 包装 — convert_to_event_stream → SSE 事件流
  • 前端 — 接收 workflow_started → node_started → text_chunk → workflow_finished

05改进方向

🔴 高优先级（P0）

  • 配置热生效 — Dify 改完即生效，本项目需重启/手动装配
  • 工具动态加载 — 参考 Plugin System，工具元数据从数据库获取，而非硬编码在代码里
  • LLM 输出可靠性 — 用 JSON Schema / 结构化输出替代关键词匹配，避免模型升级即失效

🟡 中优先级（P1）

  • 人机协同 (HITL) — 关键步骤支持暂停 → 人工审核 → 继续，补齐企业场景
  • 调试可视化 — 每个 Step 的输入/输出/Duration 可回放，降低排查成本
  • 触发器 (Trigger) — 补充定时/事件驱动的任务入口
  • 知识库治理 — 支持文档更新/删除、重向量化，避免"越用越脏"

🟢 长期演进（P2）

  • 多 Agent 协作 — 借鉴 Dify Agent Node，支持多智能体编排
  • 插件市场雏形 — 至少支持工具描述从数据库配置化读取
  • 协作编辑 — 多人同时编辑流程图（技术复杂度高）

06Dify 的问题

⚠️ 主要问题

  • Agent 自主决策能力有限 — Workflow 以预定义流程为主，缺乏复杂任务的动态规划、自主推理和实时决策能力
  • 多 Agent 协作能力不足 — 缺少统一的多智能体调度机制，Agent 之间状态共享、任务协同和通信能力较弱
  • 大型 Workflow 可维护性差 — 节点数量增多后画布复杂度迅速上升，模块复用、版本管理和流程维护成本较高
  • 调用链层次较深 — 一次 Workflow 执行需要经过 Controller → Service → Generator → Runner → Entry → GraphEngine 等多个抽象层，源码阅读成本较高
  • 异步执行链路复杂 — Workflow 执行依赖 SSE、Celery、Redis Pub/Sub 等多种机制协同，调试和问题定位难度较高
